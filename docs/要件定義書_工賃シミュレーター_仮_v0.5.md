# 工賃シミュレーター 要件定義書（仮）v0.5

> 本書は、現時点の合意内容と実際の工賃表の数値を反映した仮要件定義書である。以前の「工賃記録システム」前提を外し、計算結果を保存しないシミュレーターとして定義する。

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| プロダクト | B型事業所向け工賃シミュレーター |
| バージョン | 仮 v0.5 |
| 対象 | MVP |
| 対象事業所 | 就労継続支援B型事業所 |
| 規模 | 職員・利用者合わせて約30人 |
| 主な利用者 | 利用者・職員 |
| IT専門職 | なし |
| 既存環境 | Google Workspace利用 |
| 主目的 | その日の工賃概算を利用者本人が把握する |

## 2. プロダクトの目的

利用者と職員が、その日の作業内容・作業時間・能力加点・出来高を入力し、その場で工賃概算額を確認するためのシミュレーターとする。

表示金額は正式な工賃支払記録ではない。正式な記録・支払管理は、現行の紙・Excel等による事業所運用を継続する。

MVPの責任範囲は、次のとおりとする。

```text
計算する → 本人が確認する → 終了する
```

## 3. 基本原則

- 計算結果を保存しない
- 個人情報を保存しない
- 工賃設定・単価設定をアプリから保存・編集しない
- 認証・職員Role・承認フローを設けない
- 利用者と職員が一緒に操作する
- 現場の工賃計算方法をアプリ側の都合で変更しない
- 工賃制度変更に備え、UIと計算ロジックを分離する

## 4. 基本利用フロー

```text
アプリを開く
  ↓
午前の業務を選ぶ → 午前の作業時間を入力 → 午前の能力加点を選ぶ
  ↓
午後の業務を選ぶ → 午後の作業時間を入力 → 午後の能力加点を選ぶ
  ↓
出来高を入力 → 必要なら「＋ 出来高を追加」
  ↓
金額をリアルタイム計算 → 今日の工賃概算を確認
  ↓
終了 / リセット → 入力内容・計算結果を破棄
```

## 5. AM・PMの扱い（必須）

午前と午後は独立した業務として扱う。午前と午後で異なる業務を選択できること。

```text
午前：KIIYA  150円 / 時間
午後：PC     100円 / 時間
```

したがって、「今日の業務」を1つだけ選択するUIにはしない。

## 6. 業務別時給（現行表の値）

既存表の「単価」は本アプリでは業務別時給として扱う。以下の値は、以前のプロトタイプの仮値とは区別する。

| 業務 | 時給 |
|---|---:|
| Le Milieu_農園 | 150円 / 時間 |
| Le Milieu_フィナリー | 150円 / 時間 |
| KIIYA | 150円 / 時間 |
| ルート5 | 150円 / 時間 |
| 東洋計器 | 150円 / 時間 |
| 販売会準備・片付け | 100円 / 時間 |
| 手芸 | 100円 / 時間 |
| スリーピース | 100円 / 時間 |
| PC | 100円 / 時間 |
| 就職準備 | 100円 / 時間 |
| その他内職 | 100円 / 時間 |
| 販売会（平日）参加 | 150円 / 時間 |
| シルクスクリーン | 300円 / 時間 |

制度変更時は、開発側で設定ファイルを変更し、計算テスト後に再デプロイする。

## 7. 能力加点

利用者の能力区分に応じ、午前・午後それぞれの工賃へ加算する。現行値は以下のとおり。

| 能力区分 | 加点額 |
|---|---:|
| なし | 0円 |
| A_50 | 50円 |
| B_100 | 100円 |
| C_200 | 200円 |
| D_300 | 300円 |
| E_400 | 400円 |
| F_500 | 500円 |

午前・午後の両方で `B_100` を適用した場合、能力加点は1日合計200円となる。

## 8. 能力加点の判定

MVPではシステムによる自動判定を行わない。休憩、作業時間、体調、業務状況等に応じ、その日の状況を見て職員が適切な加点を選択する。

「○分以上なら加点」といった自動ルールは実装しない。この運用で問題ないかは、後日プロトタイプを職員へ提示して確認する。

## 9. 出来高計算

```text
出来高加点 = 出来高単価 × 数量
出来高合計 = Σ（出来高単価_i × 数量_i）
```

出来高の単価・数量は業務ごとに異なるため業務マスタへ固定せず、その場で入力できるようにする。

## 10. 出来高入力（複数追加必須）

出来高は1件固定ではなく、複数追加・削除できることを必須とする。

```text
出来高①
項目名：[              ]
単価  ：[ 10 ] 円
数量  ：[ 20 ]
小計  ：200円

[ ＋ 出来高を追加 ]
```

1件につき、出来高名（自由記述）、単価（数字）、数量（数字）、単位（未確定）、小計（自動計算）を持つ。

## 11. 数値入力・バリデーション

単価・数量はキーボードから直接入力し、値の変化時に即時再計算する。「計算する」ボタンは原則設けない。

最低限、次を満たす。

- 数字以外を計算値として使用しない
- 負数を許可しない
- 極端に大きな値を制限する
- 未入力時に `NaN` 等を表示しない
- 不正入力時に工賃を誤表示しない

数量に小数を許可するかは未確定。

## 12. 工賃計算式

```text
日額工賃 = 午前工賃 + 午後工賃 + 出来高合計

午前工賃 = 午前業務時給 × 午前作業時間 + 午前能力加点
午後工賃 = 午後業務時給 × 午後作業時間 + 午後能力加点
出来高合計 = Σ（出来高単価 × 数量）
```

現時点では、作業時間を時間と分で入力する画面を想定する。円未満の端数が発生した場合は、金額を円単位で切り上げる。

### 計算表示例

```text
午前：KIIYA  150 × 2時間 + 100 = 400円
午後：PC     100 × 3時間 + 100 = 400円
出来高：10円 × 20個 + 5円 × 30個 = 350円

今日の工賃概算：1,150円
```

※出来高数値は説明用であり、実際の出来高単価を示すものではない。

## 13. 画面構成

MVPではメイン計算画面を中心に、画面数をできるだけ少なくする。

```text
今日の工賃 / やさしい表示 / ？つかいかた

① 午前
  しごと [KIIYA ▼] / 1時間 150円
  はたらいた時間 [2]時間 [0]分
  加点 [100円 ▼]
  午前の工賃 400円

② 午後
  しごと [PC ▼] / 1時間 100円
  はたらいた時間 [3]時間 [0]分
  加点 [100円 ▼]
  午後の工賃 400円

③ 出来高
  出来高① / なまえ / 1個あたり / 数量 / 小計
  [＋ 出来高を追加]

今日の工賃：午前 400円 + 午後 400円 + 出来高 200円 = 合計 1,000円
[ おわる ]
```

## 14. リセットとデータ保存

MVPでは計算に関するデータを一切永続保存しない。

保存しないもの：個人名、作業内容、午前・午後の選択、作業時間、能力加点、出来高、単価、数量、計算結果、過去履歴、操作履歴、設定変更。

`localStorage`、`IndexedDB`、Cookieも工賃データの保存用途には使用しない。入力中のみReact State等へ保持し、ページ閉鎖、リロード、「おわる」で破棄する。

共有端末を想定し、「おわる」では前の業務、時間、能力加点、出来高、計算結果が一切残らない完全初期化を行う。これは重要な受入条件とする。

## 15. 認証・権限

MVPでは認証を行わず、Roleも設けない。

```text
利用者・職員・管理者をシステム上区別しない
```

Google Auth、メール認証、パスワード、Passkey、MFA、Cloudflare Accessは実装しない。利用者と職員の双方が同じシミュレーターを利用する。

## 16. 工賃設定

MVPでは利用者・職員による工賃設定の編集機能を設けない。従来プロトタイプの「単価を編集」ボタンは削除する。

時給等はアプリ内部の設定ファイル（例：`wage-rules.ts`）に保持する。制度変更時は、開発側で設定変更、計算テスト、再デプロイを行う。

## 17. データベース・バックアップ

MVPではデータベースを使用しない。Cloudflare D1等も不要とする。

保存対象となる業務データがないため、XLSXバックアップ、インポート、復元、Google WorkspaceへのバックアップもMVPに含めない。将来、工賃履歴・個人情報・設定変更・正式記録等を保存する方針になった場合に、改めて要件定義する。

## 18. アクセシビリティ

アクセシビリティは中核要件とする。

- 白をベース、緑をアクセントとする
- 色だけで意味を判断させず、文字・形を併用する（例：`✓ 選択中`）
- 漢字が読みにくい、文字が見えにくい、色が負担、多数の操作を覚えにくい利用者を考慮する
- やさしい表示、ルビ、つかいかたビューを提供する
- PC・タブレット・スマートフォンで利用できるようにする

## 19. 文字・ルビ表示

### PC等の広い画面

通常表示では必要な漢字にルビを付ける。

```text
作業時間
（さぎょうじかん）
```

やさしい表示では原則として漢字を減らし、平仮名・平易な表現にする。

### モバイル等の狭い画面

通常表示では表示領域を考慮してルビの多用を避け、やさしい表示では平仮名中心にする。

## 20. つかいかたビュー

操作画面からいつでも「？ つかいかた」を開けるようにする。長文マニュアルではなく、次の程度の簡潔な内容とする。

```text
① ごぜんの しごとを えらびます
② はたらいた じかんを いれます
③ ごごの しごとを えらびます
④ できたかずを いれます
⑤ きんがくを かくにんします
```

## 21. 技術構成（暫定）

| 領域 | 技術 |
|---|---|
| Frontend | React |
| 言語 | TypeScript |
| パッケージマネージャー | pnpm |
| 開発環境・ビルド | Vite |
| Hosting | Cloudflare Workers Static Assets / Pages |
| DB | なし |
| Backend API | 原則なし |
| 認証 | なし |
| 状態管理 | React State |
| Validation | Zod等 |
| Unit Test | Vitest |
| E2E | Playwright |
| Accessibility | axe-core |
| CI/CD | GitHub Actions |

### 開発環境の補足

- Reactプロジェクトの依存関係管理とスクリプト実行には `pnpm` を使用する
- 開発サーバー、モジュールバンドル、環境設定には `Vite` を使用する
- パッケージマネージャーはプロジェクト内で `pnpm` に統一し、`packageManager` を `package.json` に明記する
- `pnpm-lock.yaml` をバージョン管理対象とし、CIでもロックファイルに基づく再現可能なインストールを行う

### React用テストツールの提案

手軽さとViteとの相性を重視し、以下の組み合わせを第一候補とする。

| 用途 | 提案ツール | 採用理由 |
|---|---|---|
| テスト実行・ユニットテスト | Vitest | Viteベースで設定を共有しやすく、導入・実行が軽い |
| Reactコンポーネント操作 | React Testing Library | 実際の利用者操作に近い形で画面を確認できる |
| ユーザー操作の再現 | `@testing-library/user-event` | 入力、選択、クリック、リセット等を再現できる |
| DOMマッチャー | `@testing-library/jest-dom` | 表示状態やアクセシビリティ属性を読みやすく検証できる |
| アクセシビリティ検査 | `axe-core` | 既存のA11y要件を自動検査できる |

特に最初は `Vitest + React Testing Library` だけで開始し、必要に応じて `user-event`、`jest-dom`、`axe-core` を追加する。VitestはViteを基盤とするテストフレームワークで、公式ガイドでもpnpmによる導入が案内されている。React Testing Libraryは軽量なReactコンポーネントテスト用ライブラリで、実装詳細ではなく画面上のDOMと利用者操作を中心に検証できる（[Vitest公式ガイド](https://vitest.dev/guide/)、[React Testing Library公式ドキュメント](https://testing-library.com/docs/react-testing-library/intro/)）。

#### 最初に作るテスト

1. `AM時給 × AM時間 + AM能力加点` の計算
2. PMの独立計算
3. 出来高の単価×数量と複数行合計
4. 入力変更時の合計更新
5. 「おわる」による全入力リセット
6. やさしい表示の切り替え
7. 不正な数値入力の拒否・エラー表示

#### pnpmスクリプト案

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "test": "vitest",
    "test:run": "vitest run",
    "test:coverage": "vitest run --coverage"
  }
}
```

Playwrightは、実ブラウザ上での画面確認やリリース前の主要導線確認に限定して併用する。日常的な計算ロジック・コンポーネント確認はVitest中心とし、テストを重くしすぎない。

## 22. MVP範囲

- 午前・午後の業務選択と業務別時給
- 午前・午後の作業時間と能力加点
- 出来高名、単価、数量の入力
- 複数出来高の追加・削除
- 入力中のリアルタイム計算
- 工賃内訳と日額概算表示
- 完全リセット
- やさしい表示、PCルビ、モバイル向け表示、つかいかたビュー
- 入力バリデーション

## 23. MVP外

- 計算結果保存、個人工賃履歴、個人名保存
- 職員認証、Role、承認、ダブルチェック、検印、監査ログ
- 工賃設定編集、単価変更画面
- D1、バックアップ、XLSX、インポート、復元
- 月次集計、正式工賃支払記録

## 24. 現時点で残る未確定事項

### 優先度高

- 時間の入力・計算単位（1分単位まで対応するか）
- 端数をAM/PMごと・出来高合計・日額合計のどの単位で切り上げるか
- 出来高数量に小数を許可するか
- 出来高の単位（個、枚、セット、回、本、袋等）
- 出来高名称を毎回入力するか、単価×数量だけでよいか

### 優先度中

- 午前または午後に作業しない場合の表示（例：「作業なし」）
- 午前または午後に複数業務を行う場合の扱い
- 能力加点の表示名称（`A_50`、能力A、加点50円等）

## 25. プロトタイプ確認時の質問

職員へはIT用語を使わず、次を確認する。

- 午前中に2種類以上の仕事をする日はありますか？
- 15分など、1時間未満の作業時間はどのように計算していますか？
- 出来高の単位は「個」「枚」など複数ありますか？
- A〜Fという表記を利用者にもそのまま見せて問題ありませんか？
- 途中で休んだ場合などの加点を、その場で職員が選ぶ形で問題ありませんか？

## 26. MVP受入条件

### 計算

- 業務選択によって正しい時給が設定される
- AM・PMを別々に計算できる
- AM・PMの能力加点を別々に設定できる
- 複数の出来高を追加・削除できる
- 各出来高の単価×数量を計算し、全件を合算できる
- AM＋PM＋出来高が合計表示される
- 入力変更時に即座に再計算される

### データ

- DBへ工賃を保存しない
- `localStorage` 等へ工賃を保存しない
- 「おわる」で入力内容を初期化する
- 次の利用者へ前の入力内容を残さない

### UI

- 利用者と職員の双方が操作できる
- PC通常表示で必要なルビを表示できる
- やさしい表示に切り替えられる
- モバイルで平仮名中心の表示ができる
- 工賃合計が明確に見える
- 「つかいかた」をいつでも確認できる

## 27. 現在の設計上の最大の確認ポイント

最も画面設計を変える可能性が高いのは、「午前または午後の中で、複数の業務をすることがあるか」である。

```text
午前・午後それぞれ1業務 → 現在のAM/PMブロックで対応
午前に複数業務         → AM内に「＋ 業務を追加」が必要
```

プロトタイプ確認時に、実際に複数業務があるかを確認してから画面構造を確定する。

## 28. 根拠となるデータ・資料

- 業務別時給および能力加点：今回提供された実際の工賃表
- 工賃計算構造：提示された「業務別時給＋AM/PMの能力加点＋出来高単価×数量」という現行運用
- アクセシビリティ：WCAG 2.2の色に依存しない情報提示、文字拡大、操作対象サイズ等の原則、およびHTML `ruby`による日本語の読み補助

# 工賃記録アプリ 要件定義書レビュー

## 1. レビュー対象と結論

- 対象文書：[工賃記録アプリ 要件定義書（仮）v0.3](./要件定義書_工賃記録アプリ_仮_v0.3.md)
- レビュー日：2026-09-01
- 判定：**条件付きで詳細設計へ移行可能。ただし、優先度Aの項目を決定するまでDB・権限・状態遷移の確定設計は開始しない。**

v0.3は、現行の「紙→Excel」運用から段階的に移行する方針、職員による転記をMVPに含める方針、過去記録をSnapshotで再現する方針、バックアップを復元試験まで含める方針が明確である。

一方、詳細設計に直結する以下が未確定である。

1. 何を正式記録・正本とするか
2. 誰がどの操作で記録を確定・訂正できるか
3. 工賃計算の業務ルールと金額の丸め方
4. 利用者・職員・代理入力の識別方法
5. 個人情報、バックアップ、復元、保存期間の扱い

## 2. 良い点

### 業務移行

紙運用を前提に職員転記をMVPに含めており、現場の導入障壁が低い。利用者直接入力を「画面の設計対象」と「本番運用」に分けている点も妥当である。

### 記録の再現性

確定時点の時給、工程単価、計算ルールVersion、計算結果をSnapshotとして保存する方針は、過去記録の再現に必要な中核要件である。

### 復旧性

バックアップを単なるファイル出力ではなく、空のテスト環境への復元試験まで含めている。これは受入条件として特に重要である。

### アクセシビリティ

やさしい表示、ルビ、説明ビュー、色だけに依存しない操作などが要件化されている。後付けではなく基本仕様として扱っている点はよい。

## 3. 詳細設計前に決定必須の事項（優先度A）

以下は未決定のまま詳細設計を進めると、DB・API・画面・監査ログを作り直す可能性が高い。

| ID | 決定事項 | 最低限決めること | 決定者 |
|---|---|---|---|
| A-01 | 正式記録・SSOT | 紙、Excel、アプリのどれを正本とするか。不一致時の正本と訂正方法 | 事業所責任者 |
| A-02 | 初期運用方式 | MVP開始時は職員転記のみか、利用者直接入力も使うか | 事業所責任者 |
| A-03 | 確定権限 | 誰が `finalized` にできるか。一般職員・管理者の差 | 事業所責任者 |
| A-04 | 訂正方式 | 確定後に直接編集するか、訂正記録を追加するか。再承認が必要か | 事業所責任者 |
| A-05 | 工賃の計算単位 | 日単位、作業単位、月単位のどれで計算・確定するか | 事業所責任者 |
| A-06 | 時間計算 | 入力単位、休憩、複数回入力、日またぎ、端数処理の方法とタイミング | 現行規程・責任者 |
| A-07 | 工程数量計算 | 1個単位、一定数量ごと、余りの扱い、複数工程の扱い | 現行規程・責任者 |
| A-08 | グレード運用 | 意味、決定者、適用日、変更履歴、利用者画面に表示するか | 事業所責任者 |
| A-09 | 利用者識別 | 一覧、番号、QR等。誤選択防止と本人確認の方法 | 現場職員 |
| A-10 | 記録の保存期間 | 紙・Excel・アプリ・監査ログ・バックアップそれぞれの保存期間 | 事業所責任者 |

### 決定記録の形式

各項目は口頭で済ませず、次の形式で確定する。

```text
決定ID：A-01
決定内容：＿＿＿＿＿＿＿＿
理由：＿＿＿＿＿＿＿＿
決定者：＿＿＿＿＿＿＿＿
決定日：＿＿＿＿＿＿＿＿
影響範囲：画面 / DB / 権限 / 監査 / 受入試験
```

## 4. 追加で明示すべき業務要件

### 4-1. 工賃計算

- 金額は整数円で扱うか、小数を許容するか
- 時間の単位を分で保存するか、時間と分を別々に保存するか
- 時給×時間の端数を、工程加算前・後・日次・月次のどの時点で処理するか
- 作業時間の上限、0時間、負数、異常に長い時間を許可するか
- 数量の上限、0個、負数、整数以外を許可するか
- 工程単価が適用されない場合の扱い
- 工賃が0円になる記録を許可するか
- 同一日に同一利用者の複数記録を作れるか、統合するか
- 作業日と入力日・確定日を別々に持つか
- 休日、欠勤、遅刻、早退、休憩を記録対象に含めるか
- 計算結果を再計算できるか。再計算時に元結果を保持するか

### 4-2. 入力・確認・確定

- 職員転記は入力後すぐ確定できるか、確認待ちを経由するか
- `draft` を誰が閲覧・編集・削除できるか
- `returned` の差し戻し理由を必須にするか
- 提出者と確定者が同一人物でもよいか
- 代理入力時に、原資料（紙）の識別情報を残すか
- 確定時に確認した項目を記録するか
- 確定済み記録を再オープンする場合の承認者と理由
- 保存失敗・二重送信・通信切断時の扱い

### 4-3. 利用者情報

- 氏名以外に保存する情報（利用者番号、読み、表示名等）
- 氏名の表示範囲と、一覧画面でのマスキング要否
- 利用終了者の扱い（非表示、履歴閲覧、削除不可）
- 同姓同名や読みが同じ利用者の識別方法
- 職員が利用者を登録・変更・無効化できる範囲
- 利用者本人の直接入力を採用した場合の「本人確認」の方法

## 5. 権限・セキュリティで追加すべきこと

現状は「職員認証」と「Role確認」まで定義されている。詳細設計前に、Roleと操作の対応表を作る必要がある。

| 操作 | 利用者 | 一般職員 | 管理者 | 備考 |
|---|---:|---:|---:|---|
| 利用者選択・入力 | 暫定 | ○ | ○ | 直接入力採用時 |
| 紙記録の転記 | — | ○ | ○ | MVP必須 |
| 工賃の確定 | 未確定 | 未確定 | 未確定 | A-03で決定 |
| 確定後訂正 | — | 未確定 | 未確定 | 理由・再承認要否 |
| 単価・工程変更 | — | 未確定 | 未確定 | 適用開始日を含む |
| バックアップ出力 | — | 未確定 | 未確定 | 個人情報を含む |
| バックアップ復元 | — | 未確定 | 未確定 | 原則、限定権限を推奨 |
| 監査ログ閲覧 | — | 未確定 | 未確定 | 改ざん防止を含む |
| 利用者の無効化 | — | 未確定 | 未確定 | 削除ではなく無効化を推奨 |

追加で決める項目：

- Cloudflare Accessの許可対象（ドメイン、Googleグループ、個別メールアドレス）
- ログインセッションの有効期限、ログアウト、共有端末での切替
- 職員退職・異動時のアクセス停止手順
- 利用者画面で前の利用者の氏名・工賃が残らない画面リセット要件
- 個人情報を含むバックアップの暗号化、保存先、共有禁止、廃棄方法
- 監査ログの削除・変更を誰にも許可しないか
- 不正アクセス・誤操作・情報漏えい時の対応者と連絡手順

## 6. データ設計前に明示すべきこと

### 必須の識別子・日時

少なくとも次を区別する。

```text
record_id          工賃記録のID
participant_id     利用者ID
work_date          作業日
entered_at         入力日時
entered_by         入力者
entry_source       入力方法
submitted_at       提出日時
finalized_at       確定日時
finalized_by       確定者
updated_at         最終更新日時
```

タイムゾーン、日付の基準（日本時間）、IDの採番方式、同じ記録の二重登録防止キーも決める。

### Snapshotの範囲

Snapshotは金額だけでなく、当時の表示名・読み・単位・ルール・入力値・計算結果を含めるか決定する。マスタIDだけでは、後から名称や読みを変更した場合に画面表示を再現できない。

### 削除方針

利用者、工程、グレード、単価、計算Policy、工賃記録、監査ログについて、物理削除を許可するかを定義する。正式記録と監査ログは、原則として削除ではなく無効化・訂正記録・保持期間経過後の管理削除を検討する。

## 7. バックアップ・復元の追加要件

v0.3の復元試験方針はよい。さらに次を明示する。

- バックアップファイルの完全性確認（ハッシュや署名の要否）
- ファイルの暗号化・パスワード保護の要否
- 同じバックアップを二度復元した場合の重複防止
- 復元対象（全置換、追加、差分）の方式
- 復元前のDBスナップショット取得
- 復元の取り消し・ロールバック方法
- 復元できないデータがある場合の全体失敗／部分成功の扱い
- スキーマVersionの互換性と、古いバックアップの移行方針
- 復元操作の実行可能者、承認者、立会い要否
- 定期的な復元訓練の頻度と記録
- バックアップの保存場所、保持世代、保存期間、廃棄手順
- XLSXのセル型・日付・金額・文字コード・数式の扱い

特に「復元対象が全置換か追加か」は、誤操作時の影響が大きいため、実装前に決定する。

## 8. 非機能要件の具体化

現在の非機能要件は方向性が中心なので、測定可能な条件にする。

| 分類 | 追加して決めることの例 |
|---|---|
| 性能 | 主要画面の表示時間、保存完了までの時間、同時利用者数 |
| 可用性 | 目標稼働時間、障害時の復旧目標（RTO）、許容データ損失（RPO） |
| 対応ブラウザ | Chrome / Safari / Edge等の対象バージョン |
| 対応端末 | 画面幅、縦横、タッチ操作、共有端末の条件 |
| オフライン | PWAでオフライン入力を許可するか。許可する場合の同期競合 |
| セキュリティ | パスワード・Cookie・CSRF・CSP・依存関係更新の方針 |
| 監視 | エラー通知、稼働監視、ログ保持、個人情報のログ出力禁止 |
| 保守 | リリース手順、ロールバック、DBマイグレーション手順 |
| コスト | Cloudflare、GitHub、Google Workspace等の月額上限 |
| アクセシビリティ | 実利用者テスト、キーボード、スクリーンリーダー、拡大表示、コントラストの確認方法 |

## 9. 受入条件への追加提案

### 業務ルール

- 職員が紙記録を転記し、入力元 `staff_transcription` と入力者を確認できる
- 同じ入力条件に対して、画面表示とサーバー計算結果が一致する
- 単価変更後も、変更前に確定した記録の金額・内訳・表示が変わらない
- 差し戻し理由と差し戻し者を確認できる
- 確定後の訂正が、元記録を消さずに履歴として追跡できる
- 0、空欄、上限超過、負数、桁あふれ等の入力が適切に拒否される

### 権限・情報保護

- 一般職員が管理者限定操作を実行できない
- APIを直接呼び出してもサーバー側Roleチェックを通過しない限り操作できない
- 共有端末で利用者を切り替えたとき、前利用者の情報が残らない
- バックアップファイルに含まれる個人情報を確認でき、許可された職員だけが出力・復元できる

### 復旧

- 本番相当データを空の環境に復元できる
- 復元後の件数、合計、Snapshot、状態、監査ログが一致する
- 復元失敗時に元のDBが変更されない
- 復元操作自体が監査ログに残る

## 10. 詳細設計へ進むための成果物

優先度Aの決定後、詳細設計では少なくとも次を作成する。

1. 業務用語・状態・権限の用語集
2. 業務フロー図（紙転記・直接入力・差し戻し・訂正・復元）
3. 状態遷移表と状態ごとの操作権限表
4. 計算ルール仕様書（入力・式・丸め・境界値・例題）
5. 画面一覧、画面遷移、入力項目・エラー表示仕様
6. ER図、テーブル定義、Snapshot・Version設計
7. API一覧、リクエスト／レスポンス、認可要件、冪等性設計
8. 監査ログ仕様と保存・閲覧制御
9. バックアップファイル仕様、復元仕様、互換性方針
10. 非機能要件の測定方法とテスト計画
11. 受入テスト仕様書
12. 運用手順書（ログイン、日次業務、訂正、バックアップ、障害時）

## 12. 最終コメント

v0.3は、MVPの方向性を決める要件定義としては十分に前進している。次に必要なのは機能を増やすことではなく、正式記録・計算・権限・訂正・復旧の責任境界を決めることである。

特に、**A-01（正本）、A-03（確定権限）、A-04（訂正方式）、A-06〜A-07（計算ルール）**を先に確定する。これらが決まれば、詳細設計のDB・状態遷移・API・画面仕様を安定して作成できる。
